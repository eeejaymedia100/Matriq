# Matriq — Production Development Directive

**This is the highest-authority document in this project.** Where anything elsewhere in this
doc set (`agenda.md`, `security.md`, or anything under `docs/`) is silent, ambiguous, or in
tension with what's written here, this document wins. Everything else should be read as
*supporting detail* underneath the standard set here, not a parallel or competing authority.

Read this in full before writing any code, and re-read it any time a decision feels like it's
drifting toward "make it look like an app" instead of "build the actual product."

---

## 1. Core Objective

Matriq is not a vibe-coded prototype.

The goal is to build a real, production-quality mobile application for Android and iOS that can
eventually be used by real students and institutions.

The development process must prioritize:

- Correctness
- Reliability
- Security
- Maintainability
- Accessibility
- Performance
- Good UX
- Consistent visual design
- Proper engineering practices
- Proper legal and privacy foundations
- Testability
- Production readiness

Do not optimize for generating large amounts of code quickly.

Do not make assumptions simply to keep coding.

Do not create fake functionality just to make screens appear complete.

When requirements are unclear, inspect the existing documentation first. If the documentation
does not answer the question, identify the ambiguity explicitly and make a deliberate
engineering decision rather than silently inventing a requirement.

## 2. Source of Truth

The Matriq documentation directory is the primary source of truth for the product.

Before implementing anything, read and understand every relevant document in `docs/` (and this
file, and `agenda.md`, and `security.md` at the repo root).

Do not start by blindly generating application code.

First:

1. Read all documentation.
2. Understand the product requirements.
3. Understand the existing technical decisions.
4. Understand the current implementation state.
5. Read `docs/progress-log.md` carefully.
6. Identify contradictions between documents.
7. Identify missing requirements.
8. Identify technical risks.
9. Produce an implementation plan.
10. Only then begin implementation.

Do not overwrite documented decisions without a reason.

If two documents conflict, identify the conflict and resolve it deliberately — flag it in
`docs/progress-log.md` and, per `docs/agent-workflow.md`, escalate to a human if the resolution
isn't clearly yours to make alone.

## 3. Anti-Vibe-Code Standard

Matriq must not look or behave like an application generated by blindly prompting an AI.

The following are explicit quality failures. Do NOT use:

- AI-slop photographs
- Random AI-generated people
- Generic stock photography without a product reason
- Fake 3D renders just for decoration
- Excessive gradients
- Excessive glowing effects
- Excessive glassmorphism
- Decorative elements without purpose
- Random blobs or abstract shapes
- Cursive fonts without a strong branding justification
- Generic typography
- Emoji icons
- Text-only logo where a proper brand identity is required
- Missing favicon or application icon
- Inconsistent icon styles, spacing, typography, border radii, or colors
- Excessive shadows

The visual system must be deliberate and consistent. See `docs/design-system.md`.

## 4. Anti-Animation Rule

Do not add animations simply because animations are possible.

Avoid: animation on every section, scroll animations everywhere, unnecessary parallax, excessive
page transitions, bouncing elements, attention-seeking microanimations, long animations that
slow down the user, decorative motion.

Animations should only exist when they improve feedback, understanding, navigation, state
transitions, or perceived responsiveness.

The application should still feel excellent when animations are disabled.

## 5. Functionality Standard

Every visible interactive element must work.

Do not create broken buttons, dead navigation, fake forms, fake loading screens, fake payment
confirmations, fake QR verification, fake authentication, fake API responses presented as real
functionality, placeholder data accidentally shipped as production data, or screens that lead
nowhere.

If something has not yet been implemented, it should be clearly represented as an internal
development state rather than pretending to be functional.

Every feature must have: loading state, success state, empty state where appropriate, error
state, validation, recovery path, appropriate feedback.

Do not use generic "Something went wrong" messages when a useful error explanation can be
provided.

## 6. UX Standard

Matriq should feel like a serious product.

Prioritize: clear information hierarchy, simple navigation, predictable interactions, consistent
components, fast feedback, accessible controls, proper touch targets, good contrast, readable
typography, sensible empty/error states, clear confirmation states.

Do not make the interface complicated just to make it look sophisticated. The interface should
feel simple because the underlying system is well designed.

## 7. Design System

Before building large numbers of screens, establish a coherent design system. Define and
consistently use: typography (families, sizes, weights, line heights), colors, backgrounds,
borders, border radii, shadows, spacing, buttons, inputs, cards, navigation, modals, toasts,
alerts, icons, loading indicators, empty states, error states.

Do not create slightly different versions of the same component unless there is a deliberate
reason. See `docs/design-system.md`.

## 8. Branding

Matriq requires a proper product identity. Do not rely on a simple text-only logo.

The product should have: a proper Matriq logo, app icon, favicon, appropriate splash screen,
consistent brand typography and colors, correct light/dark considerations where applicable, and
correct Android and iOS application metadata.

Branding should feel intentional rather than generated as an afterthought.

## 9. Copywriting Standard

Product copy must sound natural and human.

Avoid generic AI marketing language, empty buzzwords, overly dramatic claims, unnecessary
jargon, repetitive explanations, excessive em dashes, clichés, and artificially polished
corporate language.

Do not repeatedly use em dashes as a substitute for proper sentence structure.

Keep copy clear, direct, human, concise, useful.

## 10. Legal and Privacy Requirements

Privacy Policy and Terms & Conditions are first-class product requirements. They must not be
added as an afterthought immediately before release.

Matriq has a dedicated legal area: `docs/legal/`, containing `privacy-policy.md`,
`terms-and-conditions.md`, `data-processing.md`, and `legal-requirements.md`.

## 11. Privacy Policy

The Privacy Policy should explain, where applicable: what personal information Matriq collects
and why, how it's used and stored and protected, who it may be shared with, third-party service
providers (payment providers, AI services, analytics, crash reporting), authentication
information, student/institution information, transaction information, QR/receipt information,
course/academic information, data retention and deletion, user privacy rights, security
practices, contact information, and how the policy itself changes over time.

Because Matriq is intended for users in Nigeria, applicable Nigerian data protection
requirements must be considered, including the Nigeria Data Protection Act and relevant
regulations. **Do not claim legal compliance without verifying the actual requirements.** See
`docs/legal/privacy-policy.md`.

## 12. Terms and Conditions

The Terms & Conditions should address, where applicable: eligibility, account creation and
responsibilities, acceptable use, prohibited activities, student/institution relationships,
payments and transaction processing, digital receipts, QR verification, refunds and payment
disputes, AI features and their limitations, third-party services, intellectual property,
service availability and maintenance, account suspension/termination, liability limitations,
dispute resolution, governing law, changes to the terms, and contact information. See
`docs/legal/terms-and-conditions.md`.

## 13. Legal Document Versioning

Legal documents must be versioned (e.g., "Privacy Policy, Version 1.0, Effective Date: [date],
Last Updated: [date]"). Do not hard-code a fictional effective date. The system should be
designed so legal documents can be updated and versioned over time.

## 14. User Consent and Acceptance

During onboarding, users should be able to access the legal documents (clickable, not just
referenced in passing). Where legally appropriate, the system should record: user, document,
document version, timestamp, and acceptance status.

Do not simply store a generic boolean such as `termsAccepted = true` without recording which
version was accepted. See `docs/data-model.md`'s `legal_acceptances` table and
`docs/backend-api.md`'s consent endpoint.

## 15. Legal AI Restriction

AI may assist with drafting, structuring, identifying missing sections, comparing requirements,
implementing legal-document pages, implementing consent tracking, and identifying technical
privacy concerns.

**AI-generated legal text must NOT automatically be presented as legally reviewed or legally
authoritative.** Privacy Policy and Terms & Conditions must undergo appropriate legal review
before production release. The engineering agent must clearly distinguish: technical
implementation, product requirements, legal requirements, and legal advice — these are not the
same thing, and conflating them is exactly the mistake this section exists to prevent.

## 16. Security

Security is not optional. The application must consider authentication, authorization, secure
sessions, password handling, token security, API authentication, input validation, rate
limiting, database security, secrets management, payment verification, webhook verification,
secure storage, data minimization, access control, audit logging where appropriate, and secure
error handling.

Never expose API keys, private keys, payment secrets, database passwords, authentication tokens,
or service credentials. Do not put secrets directly into source code.

See `security.md` for the full, binding detail — this section states the principle, that
document states the specifics.

## 17. Payment Security

Payments must be treated as a serious financial subsystem. Never trust a client-side payment
success message. Payment status should be verified through the appropriate server-side
mechanisms and payment-provider verification/webhooks. Do not mark transactions as successful
merely because "the frontend says payment succeeded." The backend must be authoritative.

Transaction states should be explicitly designed: `pending`, `successful`, `failed`,
`cancelled`, `refunded`, `disputed`. See `docs/data-model.md` and
`docs/payment-integration.md` for the full state machine.

## 18. Testing

Do not consider a feature complete merely because the screen renders. Testing should cover unit,
integration, API, database, authentication, payment, and UI tests; critical user flows; error
states; edge cases; security-sensitive flows.

Important flows should be tested end to end: registration, login, onboarding, student
verification, payment, payment failure, receipt generation, QR verification, logout,
password/account recovery, course-related functionality, AI functionality.

## 19. Development Workflow

```
DOCUMENTATION
  → ARCHITECTURE REVIEW
  → DESIGN SYSTEM
  → PROJECT SCAFFOLD
  → DATABASE
  → BACKEND/API
  → AUTHENTICATION
  → CORE MOBILE FLOWS
  → PAYMENTS
  → AI FEATURES
  → TESTING
  → SECURITY REVIEW
  → UX/POLISH
  → ANDROID BUILD
  → iOS BUILD
  → RELEASE
```

Do not skip stages simply because code can be generated quickly. (This maps directly onto the
phases in `agenda.md` — treat that phase list as the concrete schedule for this workflow.)

## 20. Implementation Loop

For every significant feature:

1. Understand the requirement.
2. Inspect existing code.
3. Inspect relevant documentation.
4. Plan the implementation.
5. Implement the smallest coherent version.
6. Run tests.
7. Run linting/type checks.
8. Inspect the actual result.
9. Fix issues.
10. Test edge cases.
11. Review security implications.
12. Commit the working state.
13. Move to the next feature.

The cycle is: **BUILD → TEST → INSPECT → FIX → COMMIT → CONTINUE.**

Never: BUILD EVERYTHING → ASSUME IT WORKS.

## 21. Git

Use Git throughout development. Make meaningful commits corresponding to coherent changes (e.g.
"initialize project structure", "implement authentication", "add payment webhook verification",
"add tests for authentication") — not one giant commit after the entire application has been
generated. Do not commit secrets.

## 22. Agent Behavior

The AI development agent must behave like a senior product engineering team. It must: read
before coding, inspect before changing, plan before implementing complex features, test before
declaring completion, verify assumptions, keep documentation updated, respect existing
architecture, avoid unnecessary dependencies/rewrites/duplicate systems/fake
implementations/over- and under-engineering, explain important architectural decisions, and
maintain project consistency.

Do not generate code merely to satisfy the prompt. Generate code that belongs in the actual
product.

## 23. Documentation Maintenance

When implementation changes the architecture, update the appropriate documentation.
Documentation must not become stale. For significant architectural changes: update the relevant
markdown file, explain the change and why it was made, record important tradeoffs, and update
`docs/progress-log.md`.

## 24. Progress Log

`docs/progress-log.md` is an important continuity mechanism. Read it before beginning work.
Update it after completing significant work. It should record what's been completed, what's in
progress, what remains, known issues, important decisions, blockers, and the next recommended
step — so another session or another agent can continue without starting from zero.

## 25. No Pretending

Never claim "Implemented" when something was merely scaffolded. Never claim "Tested" unless
tests were actually executed. Never claim "Production ready" without appropriate verification.
Never claim "Secure" without appropriate security review. Never claim "Legally compliant"
without appropriate legal verification.

Use precise language. *"Payment UI implemented, backend verification still pending"* is
acceptable. *"Payments are complete"* is not acceptable if server-side verification hasn't been
implemented.

## 26. Production Readiness

Before Matriq is considered production ready, verify: core functionality, authentication,
authorization, database reliability, API testing, payment verification, error handling, loading
states, empty states, accessibility review, security review, privacy requirements, Terms &
Conditions availability, Privacy Policy availability, legal acceptance tracking, app icon,
splash screen, favicon where applicable, correct metadata, Android build, iOS build, release
configuration, passing tests, working CI/CD, no exposed secrets, and current documentation.

Only then should the application be treated as approaching a real release.

## 27. Most Important Principle

Matriq should never be built with the mentality: **"Make it look like an app."**

It should be built with the mentality: **"Build the actual product."**

Every screen must have a reason. Every button must have a function. Every API must have a
purpose. Every database table must represent a real requirement. Every animation must have a
reason. Every piece of copy must communicate something useful. Every permission must have a
reason. Every piece of collected data must have a reason. Every payment state must be
trustworthy. Every legal document must be treated seriously. Every feature must be testable.

The final result should feel like a product created by a disciplined product, design,
engineering, security, QA, and legal-aware team — not like a collection of AI-generated screens.

The objective is not to hide the fact that AI was used. The objective is to ensure that AI is
used as an engineering tool rather than as a substitute for engineering judgment.
